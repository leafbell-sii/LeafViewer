# LeafViewer 명세서

> 상태: **초안 v0.8** · 최종 수정 2026-11-21 · 기술 스택 **확정**(Win32 + Direct2D/DirectWrite) · **M0·M1·M2 완료**(실측 §6.1.1–§6.1.3)
> 대화를 통해 계속 갱신한다. 결정이 필요한 항목은 [§12 미결 사항](#12-미결-사항)에 모아 둔다.
> 요구사항 우선순위: **P0** = v1 필수 · **P1** = v1 희망 · **P2** = 후속 버전

## 1. 개요

### 1.1 한 줄 정의

지정한 폴더를 트리로 보여 주고, 그 안의 문서(.md, .txt, .pdf …)를 즉시 열람하는 **Windows 전용 경량 문서 뷰어**. Rust로 작성한다.
**주 용도는 PDF 열람**이며, MD·TXT는 보조 포맷이다. 우선순위가 충돌하면 PDF 경험을 먼저 챙긴다.

### 1.2 설계 목표 (우선순위 순 — 충돌하면 앞의 목표가 이긴다)

| 순위 | 목표 | 의미 |
|---|---|---|
| G1 | **낮은 메모리** | 유휴·열람 중 메모리가 작고, **상한이 있다**. 모든 캐시는 예산(budget)을 가진다. |
| G2 | **빠른 반응** | 실행·파일 열기·스크롤·문서 전환이 즉각적이다. UI 스레드는 I/O를 절대 기다리지 않는다. |
| G3 | **읽기 품질** | 한글을 포함한 텍스트가 선명하다(ClearType, 올바른 폰트 대체, 정확한 줄바꿈). |
| G4 | **확장성** | 새 확장자는 핵심 코드 수정 없이 "포맷 핸들러" 추가만으로 지원한다. |

### 1.3 비목표

- 편집 기능 — 뷰어 전용. "외부 편집기로 열기"만 제공
- 크로스 플랫폼 — Windows에 최적화하는 대신 이식성을 포기
- 클라우드 동기화, 계정, 네트워크 기능
- 원격 리소스 자동 로딩

## 3. 기술 스택

### 3.1 결론

> **확정 (v0.2):** 웹 의존 기능(Mermaid·수식·HTML)이 불필요하다고 결정되어(§12 Q1) 아래 네이티브 스택으로 확정한다.
> M0 실측은 성능 목표 검증용이며, 결과가 §6.1 목표를 크게 벗어날 때만 재검토한다.
>
> 이 앱에서 "프론트엔드/백엔드"는 웹앱처럼 별도 프로세스가 아니라 **한 프로세스 안의 크레이트 경계**다.
> 프론트엔드 = `leaf-win`(창·컨트롤·그리기), 백엔드 = `leaf-core` + 포맷 크레이트(파일·파싱·레이아웃·캐시).

| 계층 | 선택 |
|---|---|
| 언어/툴체인 | Rust stable, `x86_64-pc-windows-msvc` (ARM64는 P2) |
| **프론트엔드: 창·UI 골격** | **Win32 API** (`windows` 크레이트, Microsoft 공식 바인딩) + 공용 컨트롤(TreeView, StatusBar, Edit) |
| **프론트엔드: 문서 그리기** | **Direct2D 1.1 + DirectWrite** 직접 렌더링, 이미지 디코딩은 **WIC** |
| **백엔드: 코어** | UI 비의존 순수 Rust 크레이트 (`#![forbid(unsafe_code)]`) |
| Markdown 파서 | `pulldown-cmark` (스트리밍 풀 파서, GFM 확장 지원, 빠르고 할당 적음) |
| TXT 인코딩 | `encoding_rs` + `chardetng` (Firefox가 쓰는 조합, CP949/EUC-KR 감지) |
| 대용량 파일 | `memmap2` |
| 파일 감시 | `notify` (Windows에서는 ReadDirectoryChangesW 사용) |
| PDF | **PDFium** via `pdfium-render`, 런타임 동적 로딩 (§3.5) |
| SVG (MD 내 이미지) | `resvg` (P1, feature flag) |
| 동시성 | 표준 스레드 + `crossbeam-channel`. **async 런타임 미사용** |
| 설정 | `serde` + `toml` |

라이브러리 버전은 구현 착수 시점의 최신 안정 버전으로 고정(`Cargo.lock` 커밋)한다.

### 3.2 UI 후보 비교

| 후보 | 렌더링 방식 | 유휴 메모리(추정) | 한글 텍스트 품질 | MD 렌더링 | PDF 통합 | 구현 난이도 |
|---|---|---|---|---|---|---|
| **Win32 + Direct2D/DirectWrite** ✅ | OS 네이티브, GPU 가속 | **~10–30MB** | **최상** — ClearType, 시스템 폰트 대체, IME | 직접 구현 (레이아웃 엔진) | PDFium 비트맵 → D2D, 또는 OS PDF API가 D2D에 직접 그림 | 높음 |
| Tauri 2 (WebView2) | Chromium 엔진 | ~80–150MB+ (다중 프로세스 합산) | 좋음 | 매우 쉬움 (HTML 변환) | pdf.js로 쉬움 | 낮음 |
| egui (eframe) | 즉시 모드, GPU | ~30–80MB | 보통 — 한글 폰트 수동 등록, 서브픽셀 AA 없음, 복합 셰이핑 미지원 | `egui_commonmark` 등 (품질 제한) | 비트맵 텍스처 | 중간 |
| iced | 보존 모드, wgpu | ~40–100MB | 좋음 (cosmic-text) — 단, 시작 시 시스템 폰트 스캔 비용 | 내장 markdown 위젯 (기능 제한) | 비트맵 이미지 | 중간 |
| Slint | 선언형, SW/GPU | ~15–40MB | 좋음 | 리치 텍스트 위젯 부족 → 사실상 직접 구현 | 비트맵 이미지 | 중간–높음 |
| GPUI (Zed) | DirectX + DirectWrite | 측정 필요 | 좋음 | `gpui-component` 활용 가능 | 비트맵 | 중간 — API 안정성 보장 없음, 외부용 문서 부족 |

> 메모리 수치는 각 프레임워크 빈 창 기준의 **경험적 대략치**이며 GPU 드라이버·DPI에 따라 크게 달라진다.
>
> **M0 실측 (Win32 + D2D, 빈 창, §6.1.1 기준 PC):** 하드웨어 렌더 타깃 개인 작업 집합 **31.8MB** / Private Bytes 44MB,
> 소프트웨어 렌더 타깃 **15MB** / 20MB. 차이의 대부분은 GPU 드라이버 DLL(Intel `igc64.dll`·`igd10um64xe.dll`) 로딩 비용이다 (§12 Q8).

### 3.3 추천 근거

1. **G1(메모리)에 가장 직접적이다.** WebView 계열은 브라우저 엔진 프로세스가 기본 비용으로 깔리고, wgpu 계열은 GPU 디바이스·셰이더·글리프 아틀라스 비용이 붙는다. Direct2D/DirectWrite는 OS에 이미 올라와 있는 구성요소라 앱이 추가로 지는 비용이 가장 작다.
2. **Windows 전용이므로 크로스플랫폼 프레임워크의 장점이 무의미하다.** 이식성을 위해 지불하는 비용(자체 폰트 스캔, 자체 텍스트 셰이핑, 자체 IME 처리)을 낼 이유가 없다.
3. **텍스트 품질(G3).** DirectWrite는 ClearType, 시스템 폰트 대체(라틴은 Segoe UI, 한글은 맑은 고딕 자동), 컬러 이모지, 정확한 한글 셰이핑을 OS 수준에서 제공하고 폰트 캐시도 OS 서비스와 공유한다. 문서 뷰어의 핵심 경험이 "글 읽기"이므로 가장 중요한 품질 요소다.
4. **세 포맷이 같은 그리기 표면으로 모인다.** TXT/MD → DirectWrite 텍스트 레이아웃, PDF → 페이지 비트맵(또는 OS PDF 렌더러의 D2D 직접 출력), MD 내 이미지 → WIC → D2D 비트맵. 중간 변환 계층이 없다.
5. **네이티브 컨트롤에서 공짜로 얻는 것.** TreeView는 키보드 탐색, 접근성, 지연 로딩 콜백(`I_CHILDRENCALLBACK`, `LPSTR_TEXTCALLBACK`)을 기본 제공한다 — 파일명을 컨트롤에 중복 저장하지 않아도 된다.
6. **배포가 작다.** 런타임 설치 불필요. exe 수 MB + `pdfium.dll`.
7. **주 용도인 PDF에 유리하다.** PDF는 어느 UI를 쓰든 PDFium이 그린 페이지 비트맵을 띄우는 일이므로, 차이는 "비트맵을 화면까지 옮기는 비용"과 "그 외 기본 비용"에서 난다. D2D는 비트맵을 GPU 메모리로 바로 올리고 타일 단위로 그릴 수 있으며, 브라우저 엔진 같은 기본 비용이 없다.

### 3.4 이 선택의 비용과 완화책

| 리스크 | 완화 |
|---|---|
| MD 레이아웃 엔진을 직접 만들어야 한다 (가장 큰 작업) | IR을 단순하게 유지하고 "블록 단위 레이아웃 + 가상화"만 구현. v1은 표·목록·코드·인용·이미지까지 |
| Win32 `unsafe` 코드 증가 | `leaf-win` 한 곳에 격리하고 안전한 래퍼만 노출. 나머지 크레이트는 `#![forbid(unsafe_code)]` |
| 다크 모드에서 공용 컨트롤 테마가 불완전 | TreeView에 `SetWindowTheme(.., "DarkMode_Explorer")` 적용(비공식이지만 널리 쓰임). 부족하면 트리도 D2D 커스텀 드로우로 교체할 수 있도록 트리 **모델과 뷰를 분리** |
| 문서 영역 스크린리더 미지원 | v2에서 UIA Text Pattern 제공자 구현 |
| 향후 웹 의존 기능이 필요해질 경우 (현재는 불필요로 결정) | 해당 문서를 열 때만 **WebView2를 지연 생성**하는 `Custom` 뷰 확장 지점을 남겨 둔다 (§4.3). 쓰지 않으면 비용 0 |

### 3.5 PDF 엔진

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **PDFium** (`pdfium-render`) | Chrome의 엔진. 렌더링 품질·호환성 최상, 텍스트 추출·검색·선택, 링크·책갈피 API. BSD/Apache 라이선스 | DLL 별도 배포(수 MB), 스레드 안전하지 않음 | **확정** — 검색·선택·책갈피가 P0이라 텍스트·구조 API가 필수 |
| Windows.Data.Pdf (OS 내장) | 추가 바이너리 0, `IPdfRendererNative`로 D2D 컨텍스트에 직접 렌더 | 텍스트 추출·검색·책갈피 API 없음 | 제외 — PDF P0 요구사항 충족 불가 |
| MuPDF | 빠르고 가벼움 | **AGPL** — 배포 시 소스 공개 의무 | 제외 |
| pdf.js | 품질 좋음 | WebView 필요 | 제외 |
| 순수 Rust 렌더러 (예: `hayro`) | 단일 바이너리 | 성숙도 낮음 | 추후 재평가 |

운용 원칙:
- `pdfium.dll`은 **첫 PDF를 열 때 로드**한다(`Pdfium::bind_to_library`). PDF를 보지 않는 세션의 비용은 0.
- PDFium 호출은 **전용 스레드 하나**에서만 한다.
- PDF 백엔드는 trait 뒤에 두어 교체 가능하게 한다.
- V8(JavaScript)/XFA 미포함 빌드를 사용한다 — 공격 표면 축소.

### 3.6 쓰지 않기로 한 것

| 대상 | 이유 |
|---|---|
| tokio 등 async 런타임 | 네트워크가 없고 작업 단위가 굵다(파일 하나 파싱). 스레드 몇 개 + 채널이 더 가볍고 단순 |
| `syntect` (v1) | 구문 정의 로딩에 수 MB·수십 ms. 코드 강조는 v1.1에서 지연 로딩으로 재검토 |
| `image` 크레이트 | WIC가 PNG/JPEG/GIF/BMP/TIFF 등을 바이너리 증가 없이 디코딩하고 D2D 비트맵으로 바로 연결됨 |
| `winit` | Windows 전용이므로 추상화 이득이 없고, 공용 컨트롤(자식 HWND) 통합은 순수 Win32가 더 단순 |

## 4. 아키텍처

### 4.1 크레이트 구조

```
LeafViewer/                    (Cargo workspace)
├─ crates/
│  ├─ leaf-doc/                # 문서 모델 공통 trait, Flow IR
│  ├─ leaf-core/               # 트리 모델, 파일 감시, 포맷 레지스트리, 작업 스케줄러, 설정
│  ├─ leaf-fmt-text/           # .txt — 인코딩 감지, 희소 줄 인덱스, mmap
│  ├─ leaf-fmt-markdown/       # .md  — pulldown-cmark → Flow IR
│  ├─ leaf-fmt-pdf/            # .pdf — PDFium 래퍼(전용 스레드)
│  ├─ leaf-layout/             # Flow IR → 블록 레이아웃 (텍스트 측정은 trait로 추상화)
│  ├─ leaf-win/                # Win32 창·컨트롤, D2D/DWrite/WIC 렌더러 — unsafe는 여기만
│  └─ leaf-app/                # main, 조립, 명령·단축키
├─ testdata/
├─ perf/
└─ docs/
```

의존 방향: `leaf-app → leaf-win → (leaf-layout, leaf-core, leaf-fmt-*) → leaf-doc`.
`leaf-win` 외에는 Win32에 의존하지 않으므로 나머지는 단위 테스트가 쉽다. `leaf-layout`은 `TextMeasurer` trait로 글자 폭을 묻고, 실제 구현은 `leaf-win`이 DirectWrite로, 테스트는 가짜 구현으로 제공한다.

### 4.2 스레드 모델

```
┌───────────────── UI 스레드 ──────────────────┐
│ Win32 메시지 루프 · 입력 · 레이아웃 · D2D 그리기  │
│ 블로킹 I/O 금지                               │
└──────▲───────────────────────┬──────────────┘
       │ PostMessageW(WM_APP+n) │ 작업 요청 (채널)
       │                        ▼
┌──────┴──── 워커 풀 (2–4) ─────────┐   ┌─── PDF 스레드 (1) ───┐
│ 파일 읽기 · 인코딩 감지 · MD 파싱    │   │ PDFium 전담:          │
│ 줄 인덱싱 · 이미지 디코딩 · 검색     │   │ 로드 · 렌더 · 텍스트   │
└──────────────────────────────────┘   └─────────────────────┘
┌─── 감시 스레드 (1) ───┐
│ notify → 디바운스 → UI │
└──────────────────────┘
```

- 모든 작업은 **세대 번호(generation)** 를 가진다. 선택이 바뀌면 이전 세대 결과는 버리고, 진행 중인 작업은 취소 플래그를 확인해 조기 종료한다.
- 결과는 채널로 넘기고 `PostMessageW`로 UI 스레드를 깨운다. 폴링 없음.
- 상시 렌더 루프 없음. 변경이 있을 때만 `InvalidateRect` → **유휴 CPU 0%**.

### 4.3 포맷 확장 구조

새 확장자는 아래 trait 하나를 구현하고 레지스트리에 등록하면 된다. 레지스트리는 컴파일 타임(feature flag로 포함 여부 결정) — 동적 플러그인(DLL)은 복잡도 대비 이득이 없어 v1에서 하지 않는다.

```rust
pub trait FormatHandler: Send + Sync {
    fn id(&self) -> &'static str;                     // "markdown"
    fn extensions(&self) -> &'static [&'static str];  // &["md", "markdown"]
    fn sniff(&self, _head: &[u8]) -> bool { false }   // 선택: 내용 기반 판별 (예: "%PDF-")
    fn open(&self, src: FileSource, ctx: &OpenCtx) -> Result<OpenedDoc>;
}

pub enum OpenedDoc {
    Text(Box<dyn TextDocument>),    // 줄 기반·대용량: txt, (향후) 로그, 소스 코드
    Flow(Box<dyn FlowDocument>),    // 블록 IR·리플로우: md, (향후) csv, epub, hwpx
    Paged(Box<dyn PagedDocument>),  // 고정 페이지: pdf, (향후) 이미지, xps
    Custom(Box<dyn CustomView>),    // 예외 경로: 예) WebView2를 지연 생성하는 HTML/Mermaid 뷰
}
```

뷰어는 `Text` / `Flow` / `Paged` 세 종류만 구현한다. 새 포맷은 셋 중 하나의 모델로 변환되면 뷰어 코드를 건드리지 않는다.

### 4.4 Flow IR과 레이아웃

```rust
enum Block {
    Heading { level: u8, inlines: Vec<Inline>, anchor: String },
    Paragraph(Vec<Inline>),
    List { start: Option<u64>, items: Vec<ListItem> },   // ListItem { task: Option<bool>, blocks }
    Quote(Vec<Block>),
    Code { lang: Option<String>, text: String },
    Table { align: Vec<Align>, head: Vec<Cell>, rows: Vec<Vec<Cell>> },
    Rule,
    FrontMatter(String),
    RawHtml(String),                                      // v1: 원문 그대로 표시
}
enum Inline { Text, Strong, Emph, Strike, Code, Link { href, children }, Image { src, alt },
              SoftBreak, HardBreak, FootnoteRef }
```

- **문단 1개 = `IDWriteTextLayout` 1개.** 인라인 서식(굵게·기울임·코드·링크)은 문자열 범위별 서식으로 적용하고, 인라인 이미지는 `IDWriteInlineObject`로 넣는다.
- **가상화:** 블록 높이는 처음엔 추정값(글자 수 × 평균 폭)으로 두고, 화면 ±1 화면 범위만 실제 레이아웃한다. 실제 높이가 확정되면 화면 상단 블록을 기준(anchor)으로 스크롤 위치를 보정해 튐을 막는다.
- 창 폭이 바뀌면 보이는 블록만 즉시 재레이아웃하고 나머지는 지연한다.

### 4.5 메모리 정책 (G1 구현 규칙)

| 대상 | 정책 |
|---|---|
| 열린 문서 | 현재 문서 + 최근 문서 N개(기본 2)만 파싱 상태 유지, 나머지는 해제 |
| 작은 파일 (< 16MB) | 메모리로 읽고 **파일 핸들 즉시 닫음** |
| 큰 텍스트 파일 (≥ 16MB) | mmap. 줄 인덱스는 **희소 인덱스**(1,024줄마다 오프셋 1개) → 2천만 줄 파일도 인덱스 약 160KB |
| 비 UTF-8 대용량 | 보이는 구간만 청크 단위로 디코딩 |
| PDF 페이지 비트맵 | LRU. 예산 = max(64MB, 뷰포트 바이트 × 3). 쪽 픽셀이 600만 이하면 쪽 전체 한 장, 넘으면 512px 타일 단위 렌더. 점진 표시용 저해상도(폭 256px) 쪽도 같은 예산에 포함 |
| PDFium 쪽 객체 | 열어 둔 쪽은 디코딩된 이미지를 들고 있으므로 최근 **2쪽**만 유지(M1 실측: 6쪽 대비 최대 메모리 126 → 91MB, 속도 차이 없음). 렌더는 `FPDF_RENDER_LIMITEDIMAGECACHE` |
| PDF 쪽 텍스트·링크 | 보이는 쪽만 추출, 최근 64쪽 LRU |
| MD 이미지 | 화면 표시 크기로 디코딩(WIC 스케일러), 원본 해상도로 보관하지 않음. LRU 32MB |
| DWrite 텍스트 레이아웃 | 화면 근처 블록만 보유, LRU. TXT는 행(row) 단위 레이아웃을 UTF-16 128K단위 예산으로 보유 |
| TXT 행 | 4KB(`MAX_ROW_BYTES`)보다 긴 줄은 글자 경계에서 잘라 여러 행으로 표시(FR-T06). 스크롤 위치는 (화면 맨 위 행의 바이트 오프셋, 행 안 높이)라 문서 전체 높이를 계산하지 않는다 |
| 폴더 트리 | 펼친 폴더의 자식만 메모리에. 파일명은 Rust 모델에만 저장(컨트롤은 콜백으로 조회) |
| 창 최소화 | 비트맵·레이아웃 캐시 비움 |

> **mmap 주의:** Windows에서는 매핑된 파일의 크기를 다른 프로세스가 바꿀 수 없다(`ERROR_USER_MAPPED_FILE`). 편집기 저장을 방해하지 않도록 mmap은 큰 파일에만 쓰고, 변경 이벤트를 받으면 즉시 해제 후 다시 매핑한다.

### 6.2 안정성

- 포맷 파서는 워커에서 `catch_unwind`로 격리 → 패닉 시 오류 화면. 이를 위해 release에서도 `panic = "unwind"`를 유지한다.
- PDFium 네이티브 크래시는 잡을 수 없다. 프로세스 분리는 G1과 충돌하므로 v1에서는 하지 않고, PDFium을 최신으로 유지하는 것으로 대응한다.
- 파일은 `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`로 연다 — 뷰어가 다른 프로그램의 저장·삭제를 막지 않는다.
- 크래시·오류 로그: `%LOCALAPPDATA%\LeafViewer\logs\`

### 6.3 보안

- 네트워크 접근 없음 (v1, 업데이트 확인 포함).
- 원격 리소스 기본 차단. 외부 링크는 사용자가 클릭할 때만 기본 브라우저로 연다(`http`, `https`, `mailto`만 허용).
- 링크가 가리키는 로컬 파일이 지원 포맷이 아니면 **실행하지 않고** "탐색기에서 보기"만 제공한다.
- 스크립트 실행 없음 (V8 미포함 PDFium 빌드).

### 6.4 호환성

- **Windows 11, x64만 지원**(§12 Q5). Windows 10에서 동작할 수도 있지만 보장·테스트하지 않는다. ARM64는 P2.
- Windows 11 전용이므로 다크 모드 제목 표시줄(`DWMWA_USE_IMMERSIVE_DARK_MODE`), 둥근 모서리 등 문서화된 API를 OS 버전 분기 없이 쓴다.
- 고대비 모드에서 시스템 색 사용 (P1).

## 9. 빌드 · 배포

```toml
[profile.release]
opt-level = 3
lto = "fat"
codegen-units = 1
strip = true
panic = "unwind"            # 파서 패닉 격리 (§6.2)
```

- 정적 CRT (`-C target-feature=+crt-static`) → VC++ 재배포 패키지 불필요.
- 앱 매니페스트: Per-Monitor V2 DPI, `longPathAware`, Common Controls v6.
- v1 배포: **포터블 zip** — `LeafViewer.exe` + `pdfium.dll` + 서드파티 라이선스 고지.
- PDFium 바이너리: `bblanchon/pdfium-binaries`의 V8/XFA 미포함 빌드.
- 배포 형태는 개인용 포터블 zip으로 결정(§12 Q4). 설치형(MSI/winget), 코드 서명, 자동 업데이트는 하지 않는다.
- 설정·세션 파일은 `%APPDATA%`·`%LOCALAPPDATA%`에 둔다(§8). exe 폴더에 쓰지 않으므로 어느 위치에 풀어도 동작한다.
